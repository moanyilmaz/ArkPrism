\section{Introduction}
\label{sec:introduction}

\openharmony has become a major platform for mobile, wearable, and embedded applications, with system services for location, device identity, accounts, media, sensors, networking, and inter-device collaboration~\cite{openharmony,harmonyroadmap,huaweiHarmonyWhitepaper}. These services make privacy analysis an important part of application review. Static taint analysis addresses this task by identifying values produced by privacy-sensitive APIs and checking whether they can reach logging, storage, network, or other exposure points. Its result, however, is only as reliable as the initial identification of those source values.

This paper studies the prerequisite we call \emph{privacy-source binding}: associating a platform operation with the exact program value that carries its modeled privacy data. Existing ArkTS infrastructure provides strong foundations. ArkAnalyzer constructs typed IR, control-flow graphs, call graphs, and points-to information~\cite{arkanalyzer}; HapFlow adds IFDS-based source-to-sink analysis~\cite{hapflow}. HapFlow resolves source specifications through SDK method signatures, which supports ordinary direct calls. The difficulty is that a signature alone does not always reveal either the owner of an ArkTS operation or the value produced by it. Once either relation is absent, the downstream solver cannot reconstruct the missing taint seed.

Two ArkTS characteristics make this problem systematic. First, \emph{API identity is indirect}. The same operation may move from an historical \texttt{@ohos.*} module to a consolidated \texttt{@kit.*} export, appear as an executable property, pass through an IR temporary, or be invoked on a manager returned by a factory. Matching a final member such as \texttt{get}, \texttt{create}, or \texttt{on} admits unrelated application methods; requiring one exact namespace--method form misses legitimate uses. Second, \emph{the data carrier is discontinuous}. Many APIs deliver data through a callback parameter, a fulfilled Promise value, or an \texttt{await} result rather than through the direct call result. Connecting a callback by type alone is also unsafe because a function-valued argument may be stored but never executed.

Figure~\ref{fig:motivation} illustrates both failures. The pasteboard object receives its platform meaning from the factory that created it, rather than from the final member token. The privacy value becomes available inside a callback, crosses a component field, and reaches a later UI event. A method-signature lookup can therefore miss the source owner, the callback-carried value, or both. A broad callback edge can recover the body but still cannot establish that the callback executes with the privacy payload. These are source-binding failures, not limitations of the IFDS propagation algorithm itself.

Our first insight is that no single syntactic feature is a sufficient source-identity test. Package imports are useful for narrowing candidates, receiver types identify some manager calls, factory origins identify others, and executable access form distinguishes properties from same-named constants. \mytool therefore resolves an API only when its access form has a compatible \emph{identity witness}. Common member names require a receiver, call-target, or factory witness; package proximity alone is insufficient. This design preserves valid package migrations and IR aliases without turning imported vocabulary into sources.

Our second insight is that callback execution and privacy-data transfer are separate obligations. An execution witness determines whether a continuation edge exists; a carrier contract determines which value crosses that edge. \mytool records both in an evidence-carrying source binding $\langle identity, carrier, witness\rangle$. It then re-roots the bound carrier at callback parameters and Promise success handlers within IFDS, propagates payload-dependent returns to subsequent continuations, and rejects rejection handlers, unrelated Promise owners, and constant-return transforms. The same representation covers direct returns and \texttt{await} results without introducing construct-specific source identities.

We implement these insights in \mytool, an ArkTS privacy analyzer built on ArkAnalyzer and HapFlow. Its pipeline first resolves source bindings from package exports, SDK declarations, receiver origin, access form, and ArkIR. It then propagates the bound values through initializers, closures, exceptions, access paths, callbacks, Promise chains, and lifecycle-aware entries. The output is an evidence graph that links each accepted source and carrier to its call context, sink, transfer derivation, and source location. This graph is the audit record of the two analyses rather than a separate source of inferred behavior.

The evaluation aligns each claim with an independent oracle. A source-first real-project benchmark contains 90 gold source occurrences and 96 same-name collisions; \mytool classifies all 186 at exact locations. On all 67 HapBench cases, \mytool obtains 100\% precision and specificity and 97.09\% F1, improving specificity by 28.57 percentage points and F1 by 2.65 points over HapFlow. ArkAsyncBench isolates continuation transfer: removing Promise success-handler binding loses nine positive cases, reducing recall from 100\% to 62.50\% ($p=0.00390625$), while all 24 matched negatives remain unchanged. A mutation-based Promise suite tests ownership, execution, handler position, alias separation, value dependence, sequential continuations, and flattening; \mytool classifies all 24 cases correctly. Manual source/IR review confirms all 90 sampled real-project privacy-data paths. Finally, \mytool completes \CorpusProjects{} projects without resource fallback and reports \CorpusApiOccurrences{} privacy-API usages and \CorpusPrivacyPaths{} privacy-data paths.

This paper makes three contributions:
\begin{itemize}
    \item \textbf{Privacy-source binding as an analysis problem.} We identify API-owner recovery and data-carrier recovery as coupled prerequisites for ArkTS taint analysis, and represent their result as an inspectable $\langle identity, carrier, witness\rangle$ binding.
    \item \textbf{Witness-guided identity and continuation analysis.} We combine package/export, receiver-origin, access-form, SDK, and IR evidence with carrier-aware IFDS transfer for callbacks, Promise success continuations, and \texttt{await}. The analysis distinguishes callback execution from payload transfer and retains the derivation of every reported path.
    \item \textbf{Multi-level empirical evidence.} We evaluate exact-location source binding, end-to-end flow classification against HapFlow, asynchronous semantic boundaries, manually reviewed real-project paths, and scalability over \CorpusProjects{} projects.
\end{itemize}
