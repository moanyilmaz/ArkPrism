\section{Introduction}
\label{sec:introduction}

\openharmony has moved from an emerging operating system project to a fast-growing application ecosystem for phones, tablets, wearables, vehicles, and distributed devices. Its native applications are commonly written in \arkts, a TypeScript-derived language with stricter typing, declarative ArkUI components, lifecycle callbacks, and a large family of system APIs exposed through both historical \texttt{@ohos.*} packages and newer \texttt{@kit.*} packages~\cite{openharmony,arktsdoc,harmonyroadmap}. These ecosystem properties create a timely software engineering problem: developers, platform auditors, and marketplace operators need scalable tools to recognize privacy-sensitive API usage and map where privacy-related information may flow.

This problem is especially urgent because privacy-sensitive behavior in \openharmony apps is not limited to obviously dangerous calls. An app may read hardware identifiers, query network state, access clipboard contents, subscribe to sensors, obtain location, inspect camera metadata, or create media assets through APIs that are legitimate in isolation. Whether the behavior is risky depends on where the data is obtained, how it is triggered, whether the result is displayed, logged, stored, returned, or sent over the network, and how multiple sources are combined inside a component. Thus, a useful analysis must preserve context. A flat list of sensitive calls is too shallow for auditing, while a taint-flow-only report can hide the package, permission, lifecycle, and source-code evidence that an auditor needs to validate the result.

Privacy analysis for \openharmony apps is still young. ArkAnalyzer provides the first reusable static analysis infrastructure for \arkts~\cite{arkanalyzer}; HapFlow builds an IFDS-based taint analysis framework on top of it~\cite{hapflow}; other efforts explore testing, repair, and pointer analysis~\cite{harmonyroadmap,haptest,hmtest,haprepair,arktsPointer}. However, these efforts assume that privacy-sensitive API sources are already correctly identified. HapFlow solves \emph{propagation}---whether a configured source reaches a sink---but its source configuration (\texttt{Json2ArkMethodSignature}) matches by namespace and method name against SDK declarations, and therefore cannot recognize APIs invoked through manager/helper receivers or accessed as privacy-constant fields. This is an architectural blind spot: method-signature matching is fundamentally unable to express these patterns. An auditor needs to know which privacy API was used, what package justified the match, what context reaches the API, and whether the evidence is proven or heuristically inferred.

Applying these foundations to a large and heterogeneous corpus exposes three recurring challenges in \emph{source identity resolution}. \textbf{C1: API identity is unstable under package migration.} A package migration from \texttt{@ohos.deviceInfo} to \texttt{@kit.BasicServicesKit} can make a strict rule miss a real device-identity access, while method-only matching is too noisy. \textbf{C2: Receiver-origin and property identities are invisible to method-signature matching.} ArkAnalyzer's IR lowering can split \texttt{request.agent.create} into temporary variables, and manager-style indirect calls (\texttt{cameraManager.createCaptureSession()}) have no corresponding SDK namespace entry for the receiver. Privacy-constant field reads (\texttt{deviceInfo.brand}) are not method calls at all. \textbf{C3: Asynchronous source bindings are implicit.} ArkUI callbacks may be stored in fields or anonymous builder options before they are bound to user-interface events; Promise \texttt{.then()} chains and \texttt{async-await} bridges create data-flow edges that ordinary call-graph construction does not express. These challenges motivate a system whose contribution is not replacing ArkAnalyzer or HapFlow, but solving the source identity resolution bottleneck that precedes taint propagation.

To see why the source identity bottleneck is critical, consider a concrete failure pattern. An app obtains a camera manager via \texttt{camera.getCameraManager(ctx)}, then calls \texttt{cameraManager.createCaptureSession()}. HapFlow can recognize \texttt{getCameraManager} because the namespace and method appear in SDK declarations, but \texttt{createCaptureSession} is called on the \emph{receiver object}, which has no SDK namespace entry---so no source fact is created and the IFDS solver cannot propagate taint from it. ArkPrism resolves this through receiver-origin tracing: it traces the receiver back to \texttt{getCameraManager}, identifies the enclosing \texttt{@kit.CameraKit} namespace, and creates a source fact under the resolved namespace. The bottleneck is \emph{before} taint propagation: without correct source identity, no solver improvement can recover the missing flows.

This paper targets that gap through the lens of \emph{provenance-annotated evidence subgraphs}. An information-flow subgraph is an explainable slice of an application that connects four kinds of evidence: (1) a privacy-sensitive API usage, (2) the calling context that reaches the usage, (3) downstream exposure points such as logs, UI rendering, storage, network, or data returns, and (4) semantic metadata such as permission requirements, profiling categories, and source snippets. Crucially, each edge records its \emph{provenance}---whether it was derived from call-graph edges, callback resolution, lifecycle model, IFDS propagation, or heuristic association---so that auditors can distinguish semantically proven paths from heuristic completions. The goal is not to replace taint analysis; instead, the goal is to make privacy-related behavior auditable at scale by combining API identity resolution, call-chain recovery, sink characterization, and taint propagation into a unified, provenance-tracked graph representation.

The subgraph view gives us a disciplined way to avoid two common overclaims. First, it avoids equating the existence of a sensitive API with a privacy leak: the API node is only one part of the evidence. Second, it avoids equating every taint path with a confirmed violation: sink type, trigger context, source category, and project role still matter. By preserving these distinctions, \mytool supports both automated measurement and manual triage.

We present \mytool, a static analysis framework for \arkts privacy-sensitive API identity resolution and provenance-annotated evidence subgraph mapping. \mytool is built on top of ArkAnalyzer and incorporates HapFlow-style IFDS taint analysis, with three core contributions: (1)~package- and receiver-aware API identity resolution that computes a semantic identity for each candidate usage, handling direct calls, assigned returns, manager-style indirect calls, and privacy-constant field reads while normalizing package-family equivalence; (2)~asynchronous source binding that resolves callback parameters, field-stored callbacks, builder-option callbacks, Promise chains, and async/await bridges; and (3)~provenance-annotated evidence subgraphs where each edge records its derivation. Supporting mechanisms---lifecycle modeling and context-sensitive CG---are available as configuration options but are not the primary contributions.

We evaluate \mytool on a large-scale corpus of 1,015 \openharmony/\arkts projects (31,433 source files, 238,271 methods), detecting 1,757 privacy-sensitive API usages in 236 projects, 1,352 downstream sinks, and 1,792 taint flows. On the ArkPrismBench stratified benchmark (164 projects, including 40 zero-output projects) and ArkPrismBench-Micro (77 test cases, 15 categories), \mytool achieves 100\%/100\% precision/recall and 93.2\% positive-case detection. Ablation shows: callback analysis improves taint flow recall from 51.5\% to 97.8\% ($p<0.001$); lifecycle modeling enriches structural understanding (collaboration behavior +44.2\% in quantity, precision not systematically audited) but does not increase taint flow counts; $k$-limited context-sensitive CG provides marginal precision improvement at 5.02$\times$ overhead. The full pipeline analyzes 1,015 projects in $\approx$4.2\,h wall time (2 workers) with 99.8\% completion. The evaluation is intentionally conservative: we do not treat every reported sink as a violation, and note that the corpus contains many capability demos, so \mytool provides an evidence layer for scalable audit while final security-impact claims require human review.

This paper makes the following contributions:

\begin{itemize}
    \item \textbf{Package- and receiver-aware API identity resolution.} We formulate recognizing privacy-sensitive API usages as computing $\mathit{Id}(v)=\langle\mathit{Pkg},\mathit{Ns},\mathit{Recv},\mathit{Mem},\mathit{Acc}\rangle$ for each candidate usage $v$, unifying direct invoke, assigned invoke, indirect invoke (manager/helper receivers), and privacy-constant field access. Receiver origin and privacy constants are structurally invisible to method-signature matching, explaining why HapFlow misses 31.3\% of gold API usages. The resolution handles \texttt{@ohos}/\texttt{@kit} equivalence, import aliases, and IR-lowered namespace-member aliases.
    \item \textbf{Asynchronous source binding for ArkTS.} We formalize source-consumer binding as $\mathit{SrcBind}(call, callback, param)$, with transfer rules for FunctionType/ClosureType parameters, field-stored callbacks, builder-option callbacks, Promise \texttt{.then()} chains, and \texttt{async-await} bridges. This is the dominant factor for taint flow recovery, improving recall from 51.5\% to 97.8\% ($p<0.001$), validated on 77 micro-benchmark cases across 15 categories.
    \item \textbf{Provenance-annotated evidence subgraphs.} Each subgraph edge records derivation provenance (call graph, callback resolution, lifecycle model, IFDS propagation, or heuristic association), enabling auditors to distinguish proven paths from heuristic completions. On 100 annotated subgraphs, node precision is 94--100\%, edge precision 89--92\%, provenance label accuracy 93.6\%.
    \item \textbf{Empirical evaluation on 1,015 \openharmony projects.} We construct ArkPrismBench (164 projects) and ArkPrismBench-Micro (77 cases), and demonstrate scalability ($\approx$4.2\,h wall time, 99.8\% completion). Ablation isolates each component: callback analysis dominates taint flow recovery; lifecycle modeling enriches structural understanding (+44.2\% collaboration quantity, precision not systematically audited) but does not increase flow counts; context-sensitive CG provides marginal precision at 5.02$\times$ overhead.
\end{itemize}
