\section{Background and Motivation}
\label{sec:background}

\subsection{OpenHarmony and ArkTS}
\openharmony applications are organized around abilities, pages, ArkUI components, lifecycle methods, and event callbacks~\cite{openharmony,arktsdoc,huaweiHarmonyWhitepaper}. \arkts preserves much of the TypeScript surface syntax, but introduces stricter typing and a declarative UI model. In ArkUI, a component's \texttt{build} method describes UI structure, while lifecycle callbacks such as \texttt{aboutToAppear} and event handlers such as \texttt{onClick} are implicitly invoked by the framework. These properties make \arkts attractive for application development, but complicate static analysis because important control-flow edges are not always explicit in source code.

Unlike traditional Android applications, where many lifecycle and callback conventions have been studied for years, \openharmony combines a relatively new application model with a rapidly evolving SDK. An \arkts page may contain ordinary methods, lifecycle methods, anonymous functions, class-field callbacks, Promise handlers, and declarative UI builder code in the same file. The compiler and analyzer may lower these constructs into generated methods such as \texttt{\%AM}-style anonymous methods, \texttt{\%dflt}, \texttt{\%statInit}, and \texttt{\%instInit}. These generated methods are not noise for privacy analysis: they often contain callback assignments, page initialization, or API wrapper setup. An analysis that filters them out too aggressively can lose real paths.

\openharmony also exposes a broad API ecosystem for device identity, account information, clipboard access, sensors, camera, media, location, network state, Wi-Fi, Bluetooth, telephony, calendar, and other capabilities. Some APIs have migrated from historical \texttt{@ohos.*} packages to newer \texttt{@kit.*} packages, while many apps still contain mixed imports, aliases, default imports, and manager-style APIs. For example, a project may import device information from \texttt{@ohos.deviceInfo}, from \texttt{@kit.BasicServicesKit}, or through a default alias. Similarly, APIs such as pasteboard and request-agent operations may be invoked directly from a namespace or indirectly through an object returned by a manager factory.

This evolution creates a tension: exact package matching under-reports the same conceptual API under different names, while method-name-only matching over-reports common verbs. \mytool reports both namespace-method metrics (migration-compatible) and strict package-signature metrics (alias-sensitive).

\subsection{Foundational Static Analysis for ArkTS}
ArkAnalyzer provides \arkts-aware code representation, IR transformation, Scene construction, call-graph construction, and basic data-flow support~\cite{arkanalyzer}. HapFlow builds on ArkAnalyzer to provide inter-procedural taint analysis for \openharmony, addressing lifecycle/callback entry modeling, closure-captured variables, and source/sink extraction~\cite{hapflow}.

ArkAnalyzer and HapFlow play different roles: ArkAnalyzer is a representation and graph-construction layer (Ark files, classes, methods, CFG, imports, call graphs); HapFlow is a taint-analysis layer (whether configured sources reach configured sinks). \mytool is built between and around these layers, asking a different question: can we recover the evidence that an auditor needs to understand a privacy-sensitive behavior?

Privacy auditing needs a \emph{behavior-level} explanation: what API is used, how it is reached, what exposure points are downstream, what category and permission are involved, and how patterns appear across a corpus. This distinction affects evaluation: a taint benchmark tests crafted source-to-sink cases, while a corpus audit needs API recognition against source evidence, call-chain coverage, sink distribution, and manual confirmation.

\subsection{Information-flow Subgraphs}
For each recognized privacy-sensitive API usage $u$, \mytool constructs an information-flow subgraph $G_u$ that connects four evidence layers: the API usage itself, the calling context that reaches it, downstream exposure points (sinks), and semantic metadata (package, permission, category). The formal definition is in Section~\ref{sec:design}. This evidence structure deliberately separates several levels: a privacy-sensitive API usage may be real even when no downstream sink is found; a call chain may be locally precise even when no trusted entry can be recovered; a taint path may indicate data reachability but not necessarily a policy violation.

\subsection{Motivating Example}
Listing~\ref{lst:motivation} shows a simplified \arkts pattern. The app obtains the system pasteboard, reads data in a callback, stores the text in a component state field, and later logs it from a UI interaction. A source-to-sink analyzer should report the data flow. An information-flow subgraph should additionally explain that the source belongs to the clipboard category, that it is reached from a component lifecycle or callback context, that the sink is log output, and that the source is associated with a package/namespace import.

\begin{lstlisting}[float, floatplacement=t, language=Java, caption=Simplified privacy-sensitive information flow in an ArkTS component., label=lst:motivation, style=mystyle]
import pasteboard from '@ohos.pasteboard';
import hilog from '@ohos.hilog';

@Entry
@Component
struct Index {
  @State text: string = '';

  aboutToAppear() {
    let pb = pasteboard.getSystemPasteboard();
    pb.getData((err, data) => {
      this.text = data.getPrimaryText();
    });
  }

  build() {
    Button('debug').onClick(() => {
      hilog.info(0x0, 'demo', this.text);
    });
  }
}
\end{lstlisting}

This example illustrates why a single analysis layer is insufficient: recognition must handle the indirect receiver \texttt{pb}, call-chain recovery must include lifecycle and UI callback edges, taint analysis must handle callback-provided source data, and sink analysis must classify \texttt{hilog.info} as log exposure. \mytool combines these layers in one report.

\subsection{Recurring Failure Modes}
\label{subsec:failure_modes}
Inspection of source/IR pairs and failed taint paths exposed six recurring classes: project-layout misses, package-migration mismatches, lost compound namespaces after IR lowering, unresolved manager receivers, missing callback edges, and lost callback-carried taint. We use these classes to define the analysis stages in Section~\ref{sec:design} and the case-level error taxonomy in Section~\ref{sec:evaluation}; we do not infer their corpus prevalence from the manually selected high-output projects.
