\section{Design of \mytool}
\label{sec:design}

\mytool addresses privacy-source binding in two stages. It first resolves which platform operation a statement denotes and which value, if any, carries the modeled privacy data. It then propagates that bound value while preserving the evidence used to create it. ArkAnalyzer supplies typed ArkIR, call graphs, and pointer information~\cite{arkanalyzer}; HapFlow supplies the IFDS substrate~\cite{hapflow}. \mytool adds the source-binding and continuation semantics that connect these layers.

\subsection{Privacy-Source Binding}
\label{subsec:problem_def}

\mytool accepts two related rule sets. Detector rules $R_D$ identify configured platform operations by package, namespace, member, access form, optional receiver factory, permission, and privacy category. Query rules $R_T$ additionally name an SDK owner and a concrete data carrier: a return value, an argument, or a designated callback parameter. Query rules also distinguish privacy data from explicitly modeled framework inputs. A detector rule can therefore describe a privacy-relevant operation without asserting that the operation produces a taint source.

For a candidate statement $s$ and a compatible rule $r$, the analysis returns one unit:
\begin{equation}
\mathit{ResolveUsage}(s,r)=\langle identity,carrier,witness\rangle.
\end{equation}
The identity records the normalized package/namespace, receiver owner, member, and access form. The carrier is the assigned result, a designated argument or callback parameter, or $\bot$ for detector-only evidence. The witness is the strongest compatible ownership evidence available at the statement: an imported namespace, an IR alias, an exact SDK type or call target, a traced factory origin, or an executable property read. We write $\mathit{Id}(s)$, $\mathit{Carrier}(s,r_T)$, and $w(s,r)$ for these three components. The accepted detector occurrences form $U_D$.

The binding must satisfy two independent conditions. First, the member and access form must agree with the rule and carry an access-appropriate identity witness. Second, a query source must name a concrete carrier that is valid for the resolved SDK declaration. Return sources require a non-\texttt{void} result; callback sources require a typed callback and valid callback/parameter positions; argument sources are admitted only as explicit framework inputs. The loader rejects a query rule that cannot establish this carrier contract.

For a direct return, the carrier becomes an IFDS fact at the assignment. For a callback source, the carrier becomes a fact at the designated parameter of the resolved callback edge. Promise transfer preserves the same source witness while re-rooting the carrier from the Promise object to the success-handler parameter and, when the handler returns a payload-dependent value, to the next Promise. Callback edges recovered only for call context remain distinct and cannot create a taint fact.

Each accepted occurrence and path retains this binding. The report graph links API, caller, sink, and taint-path nodes, while edge metadata records whether a relation came from the call graph, detector-local tracing, IFDS, or bounded supplementary recovery. Provenance identifies the producing analysis and transfer rule; it is not treated as a confidence score. This design makes the report an inspectable derivation of source binding and propagation rather than an additional inference layer.

\subsection{Namespace-constrained Package Migration}
\label{subsec:pkg_norm}

OpenHarmony API evolution makes exact package matching brittle, but consolidated kit packages are not globally equivalent to their historical modules. We therefore maintain a directional migration relation $\mathcal{M}$ over package--namespace pairs. For example, the \texttt{deviceInfo} export maps from \texttt{@ohos.deviceInfo} to \texttt{@kit.BasicServicesKit}, while unrelated exports in the same kit do not become compatible. A detector rule $r_D$ and import binding $i$ are compatible when they agree exactly or when $\mathcal{M}$ contains the documented export migration:

\begin{equation}
Compat(i,r_D) \triangleq
(i.pkg,i.ns)=(r_D.pkg,r_D.ns)
\lor ((i.pkg,i.ns),(r_D.pkg,r_D.ns))\in\mathcal{M}.
\end{equation}

The analyzer also derives namespace aliases from import declarations. For \texttt{import wifi from '@ohos.wifiManager'}, it records \texttt{wifi} as an alias of the canonical \texttt{wifiManager} namespace. Kit imports retain both the textual binding and the exported namespace. Matching uses the normalized package--namespace pair and member, while the report retains the raw import and SDK signature for audit.

\subsection{Package- and Receiver-aware API Identity Resolution}
\label{subsec:identity_resolution}

HapFlow's namespace--method loader resolves configured entries to SDK declarations, but its schema does not encode executable property reads or retain factory-origin evidence for manager/helper receivers. \mytool represents these access forms by computing a semantic identity and an acceptance witness for each candidate usage.

\subsubsection{Witness-guided Acceptance}

Given a candidate statement $s$, \mytool computes its member, access form, and receiver origin. Package compatibility and member agreement generate a candidate; an access-specific witness decides acceptance:
\begin{equation}
\mathit{Accept}(s,r_D) \iff
\mathit{CompatPkgNs}\land\mathit{MemberMatch}\land
\mathit{ModeMatch}\land\mathit{SufficientWitness}.
\end{equation}
Namespace calls require an imported namespace or recovered IR alias. Property rules require an executable field read. Manager calls require an exact SDK receiver type, resolved declaring-class target, traced factory origin, or exact namespace receiver. The last option is disabled for generic members such as \texttt{get}, \texttt{on}, \texttt{start}, \texttt{request}, and \texttt{close}; these members require type, target, or factory evidence. Package presence or final-token agreement alone is never sufficient.

\paragraph{IFDS source-rule acceptance.}
The IFDS query uses an exact SDK method signature whenever ArkAnalyzer resolves the call target. If the target remains unknown after frontend recovery, the fallback must match member, arity, normalized parameter types, owner evidence for generic members, and any string-dispatched event literal:
\begin{equation}
\mathit{Accept}_T(s,r_T)\triangleq
\mathit{Exact}_T(s,r_T)\lor
\bigl(\mathit{CompatibleFallback}_T(s,r_T)\land
\mathit{OwnerGuard}\land\mathit{LiteralGuard}\bigr).
\end{equation}
Exact arity is required whenever the rule declares a parameter array, including an empty one. Parameter-type comparison normalizes imported qualifiers, whitespace, array notation, callback aliases, and union order. Parameter names remain diagnostic metadata because they are not part of call semantics. Consequently, \texttt{avPlayer.on('error',...)} cannot match a configured geolocation or sensor event merely because both use \texttt{on} with the same arity. This stricter predicate governs source seeding; detector acceptance remains independent.

\subsubsection{Receiver-Origin Tracing}

The key addition beyond namespace--method loading is $\mathit{Recv}(s)$. For a statement $s: x.m(\ldots)$ where $x$ is a local or field variable, \mytool traces $x$ backward through assignments and instance-invoke bases to find its origin, subject to a tracing bound of $k_{recv}$ steps (default 8) to avoid unbounded backward exploration:

\begin{equation}
\mathit{Recv}(s) \!=\!
\begin{cases}
\mathit{Ns}(def), & x {\leftarrow} invoke(q.f()),\;f{\in}factory(r_D),\\
\mathit{Recv}(def), & x {\leftarrow} y,\;y\text{ has known origin},\\
\mathit{TF}(x), & \mathit{type}(x){=}T,\;T{\in}\mathit{SDK},\\
\bot, & \text{unresolvable in }k_{recv}\text{ steps.}
\end{cases}
\end{equation}

The first case covers the common pattern $mgr \leftarrow getManager(ctx);\; mgr.getData(cb)$, where the receiver $mgr$ originates from a privacy API factory call. The second case propagates origin through intra-procedural assignment chains and instance-invoke bases. The third case ($\mathit{TF}$) uses an exactly compatible declared SDK type. Inter-method field assignments are not claimed as origin-proven unless the defining statement or an exact type/target identity is recovered; otherwise the call is rejected. This rule avoids silently treating package import plus method-name agreement as a typed call target.

\subsubsection{Access-Kind Classification}

Each recognized usage receives an $\mathit{Acc}$ label:
\begin{itemize}
    \item $\mathit{direct}$: bare invoke statement, e.g., \texttt{id.getOAID(cb)};
    \item $\mathit{assign}$: invoke with return value assigned, e.g., \texttt{net = getDefaultNet()};
    \item $\mathit{indirect}$: invoke on a traced receiver, e.g., \texttt{mgr.getData(cb)} where $\mathit{Recv}(mgr)\neq\bot$;
    \item $\mathit{property}$: field/property read, e.g., \texttt{deviceInfo.productModel}.
\end{itemize}

\subsection{Lifecycle Context}
\label{subsec:lifecycle}

\openharmony applications follow a framework-managed lifecycle. A \texttt{UIAbility} moves through creation, foreground, background, and destruction; components move through appearance, build, visibility, and disappearance; UI handlers execute after registration. These transitions supply execution context for source bindings but do not alter their identity or carrier.

\mytool represents ability phases, component phases, and the cross-layer transitions between them. Cross-layer edges include relations such as \texttt{onForeground} to \texttt{aboutToAppear}. This explicit ordering connects source production and later consumption without treating every lifecycle method as mutually reachable.

The lifecycle modeler discovers ability classes by checking superclass inheritance from \texttt{UIAbility}, \texttt{Ability}, and extension ability base classes; component classes by checking superclass (\texttt{CustomComponent}, \texttt{ViewPU}), decorators (\texttt{@Component}), or the presence of two or more component lifecycle methods; and callback methods by scanning IR statements for \texttt{CommonMethod.*} invocations and extracting \texttt{FunctionType} arguments.

Lifecycle information is consumed in two distinct ways. For call-chain recovery, each transition $(m_i,m_j)\in\delta_a\cup\delta_c\cup\delta_{cross}$ becomes a provenance-labeled implicit edge. For IFDS, the model orders entry methods in a synthetic \texttt{DummyMain}: ability creation and foreground callbacks precede component initialization and UI callbacks, followed by background and destruction phases. The bounded default removes the standard back edge from the final entry to the loop header, preventing arbitrary destruction-to-creation cycles. Repeatable event classes may receive one additional explicit firing, but no unbounded loop. The IFDS solver derives interprocedural targets from the Scene and pointer information; it does not consume the separately augmented report call graph.

\subsection{Asynchronous Carrier and Context Recovery}
\label{subsec:async_binding}

\openharmony privacy APIs often deliver sensitive data through asynchronous callbacks and Promise chains rather than direct return values. For example, \texttt{geoLocationManager.getCurrentLocation(callback)} passes location data to a callback parameter, while \texttt{wifiManager.getLinkedInfo().then(callback)} delivers Wi-Fi state through a Promise resolution. Standard call-to-return propagation does not by itself establish the connection between a source invocation and a callback parameter or Promise resolution, so these constructs require explicit transfer rules.

\mytool formalizes carrier binding as $\mathit{SrcBind}(call, cb, param)$ (Section~\ref{subsec:problem_def}). The five rules occupy two analysis domains. T1 and T4 add construct-specific IFDS call flow, T5 follows native normal flow over the explicit ArkIR \texttt{await} use, and T2--T3 recover callback context for the report graph without manufacturing taint facts. \subsubsection{Callback ICFG Edges and Fact Domain}

ArkAnalyzer represents an arrow function argument with a \texttt{FunctionType} carrying its generated method signature; \texttt{ClosureType} additionally records the lexical environment. \mytool applies this typed lookup to every statement containing an invocation, including assignments such as \texttt{q = p.then(cb)}. A function type alone does not establish execution. The ICFG admits a callback edge only when one of four witnesses is present: a configured callback-source contract, a lifecycle-governed ArkUI event, a registered platform task with the expected owner and callback position, or the fulfillment handler of a witnessed Promise owner.

Promise ownership is established by a Promise receiver or target, a configured \texttt{Promise<T>} source, or a receiver-qualified SDK declaration whose arity-compatible overloads all return a Promise. Callback-returning overloads and resolved application methods named \texttt{then} do not satisfy this condition. ArkUI and platform-task edges expose executable callback context but carry no privacy payload unless a source binding independently supplies one. Other function-valued registrations remain report context and are not converted into execution.

An evidence-carrying fact is
\begin{equation}
d=\langle v,\alpha,\kappa,\epsilon,\delta\rangle,
\end{equation}
where $v$ is the root ArkIR value, $\alpha$ is its field or array access path, $\epsilon$ is immutable source evidence, $\delta$ is transfer metadata, and $\kappa$ distinguishes a direct value, Promise payload, callback payload, or framework argument. Fact identity includes $\langle v,\alpha,\epsilon,\kappa\rangle$; transfer metadata does not create a new semantic fact. Promise binding uses
\begin{equation}
\mathit{ReRoot}(d,v',\kappa')=
\langle v',\varnothing,\kappa',\epsilon(d),\delta(d)\rangle,
\end{equation}
which clears the container's access path while preserving its source witness and accumulated derivations.

\subsubsection{T1: Callback Parameter Binding}

When an $R_T$ source accepts a callback argument at position $i$, T1 resolves the compiler-provided function signature to a callback method with a CFG and binds only the payload parameter selected by the rule. Because \texttt{ClosureType} refines \texttt{FunctionType}, this lookup also preserves the lexical environment. Definition-backed recovery remains available only in the separately labeled report/supplementary analysis; it cannot manufacture an IFDS edge. For \texttt{getData((err,data)$\Rightarrow$...)}, T1 binds \texttt{data}, not every callback parameter.

The tracer seeds only $param_j$ selected by $r_T.i_{src}$, not every callback parameter. It propagates through ArkIR value-use edges and assignments, and accepts a sink only when a sink argument structurally depends on the current fact. IR-local names are never compared by substring, and control dependence alone does not constitute an explicit data-flow edge.

\subsubsection{T2: Field-Stored Callback Binding}

ArkUI components frequently store callback functions in class fields (e.g., \texttt{this.handler = () => \{...\}}). The callback is registered with a framework API at a later point, creating a temporal gap between definition and invocation. \mytool reads the field value at the registration site and traces it to the assignment, adding $Read(this.f)\to cb$ to the report call graph. This handles the pattern where \texttt{this.onSelect} is passed to \texttt{List.onSelect(this.onSelect)} in a component's build method. T2 supplies entry/call context; it does not by itself assert a sensitive carrier or inject an IFDS fact.

\subsubsection{T3: Builder-Option Callback Binding}

ArkUI builder APIs accept configuration objects whose fields are callback functions (e.g., \texttt{bindPopup(\{builder: popupBuilder\})}). T3 extracts the callback from a named option field, $Arg(bld,f)\to cb$, and adds the recovered owner--builder edge to the report call graph. The pattern is structurally distinct from T1 because the callback is nested inside a lowered object initializer rather than passed as a positional source callback. As with T2, the edge provides call context and is not an IFDS seed.

\subsubsection{T4: Promise Success-Continuation Binding}

Promise \texttt{.then()} carries the receiver's resolved value into the success handler's first data parameter. For call site $s:b.\texttt{then}(a_0)$, resolved callback $cb=Resolve(a_0)$, and incoming fact $d$, \mytool extends the IFDS call-flow function with
\begin{equation}
\mathcal{F}_{call}^{then}(s,cb,d)=
\begin{cases}
\{\mathit{ReRoot}(d,cb.param_0,\mathit{CallbackPayload})\}, &
\mathit{PromiseGuard}(s,d)\land\mathit{Root}(b,d),\\
\emptyset, & \text{otherwise}.
\end{cases}
\end{equation}
Here $\mathit{Root}(b,d)$ requires $\alpha(d)=\varnothing$ and exact value identity or an available pointer alias between $b$ and $v(d)$. A property of a Promise object is therefore not rebound as its resolved payload. $PromiseOwner(s)$ proves that the success callback may execute; it does not itself create sensitive data. $\mathit{PromiseGuard}$ separately requires $\kappa(d)=\mathit{PromisePayload}$, an immutable source witness whose carrier is \texttt{Promise<T>}, and the owner evidence above. Consequently, a non-sensitive SDK Promise may expose a callback body containing a later source, but its resolved value is not reclassified as privacy data. The re-rooted fact preserves $\epsilon(d)$ and records \textsc{PromiseThen}. Rejection handlers and unrelated callback positions receive no fact.

For an assigned continuation $s:q=b.\texttt{then}(cb)$, taint reaches $q$ only through a tainted callback return:
\begin{equation}
\mathcal{F}_{ret}^{then}(return\;x,s,d)=
\begin{cases}
\{\mathit{ReRoot}(d,q,\mathit{PromisePayload})\},&
\mathit{Returned}(x,d),\\
\emptyset,&\text{otherwise}.
\end{cases}
\end{equation}
$\mathit{Returned}(x,d)$ holds when normal flow has produced a fact whose structured value matches the return operand $x$; thus an alias or property-derived value can match with its access path intact, whereas mere control dependence or consumption by a constant-returning transform cannot. This return-flow rule records \textsc{PromiseReturn}, supports sequential continuations and Promise flattening, and rejects a chain whose first handler returns an independent constant.

\subsubsection{T5: Native Async/Await Normal Flow}

For \texttt{data = await promiseMethod()}, ArkIR exposes a use from the resolved Promise value to \texttt{data}. The native normal-flow function therefore maps the Promise payload to the assignment target and its later uses; no continuation-specific call-flow rule is required. A bounded fallback handles wrapper Promises whose executor-to-\texttt{await} relation is absent from ArkIR, and labels those outcomes as supplementary rather than IFDS-derived.

\subsubsection{Algorithm}

Algorithm~\ref{alg:callback} gives the T4 extension to IFDS call flow. It executes on an edge in $E_{then}$, not after solver termination. Promise-payload facts bypass positional argument mapping: the resolved value is not an ordinary argument of \texttt{then}. Non-payload facts may still enter through exact lexical captures. The transfer is monotone and adds a source-preserving fact only when Promise ownership, payload state, root identity, and callback-position evidence hold.

\begin{algorithm}[H]
\caption{Promise success-continuation IFDS call flow}
\label{alg:callback}
\footnotesize
\begin{algorithmic}[1]
\Require Call site $s$, resolved callee $m$, incoming fact $d$
\Ensure Call-flow facts $D'$
\If{$(s,m)\notin E_{then}$}
  \State \Return $\Call{StandardCallFlow}{s,m,d}$
\EndIf
\If{$d=\mathbf{0}$}
  \State \Return $\{\mathbf{0}\}$
\EndIf
\If{$\kappa(d)\neq\mathit{PromisePayload}$}
  \State \Return $\Call{CapturedCallFlow}{s,m,d}$
\EndIf
\State $D' \gets \emptyset$
\If{$\Call{PromiseGuard}{s,d} \land \Call{Root}{s.base,d}$}
  \State $d' \gets \Call{ReRoot}{d,m.param_0,\mathit{CallbackPayload}}$
  \State $d'.derivation \gets d'.derivation\cup\{\textsc{PromiseThen}\}$
  \State $D' \gets D'\cup\{d'\}$
\EndIf
\State \Return $D'$
\end{algorithmic}
\end{algorithm}

Relative to the resolved callback edge and available alias relation, this transfer follows Promise success semantics: every accepted fact denotes a modeled Promise payload that may be supplied as the first success-handler argument. The guard excludes \texttt{catch}, rejection callbacks, nonzero callback positions, custom resolved \texttt{then} owners, and receiver facts without Promise-payload state. The source witness is copied rather than reconstructed, so source-distinct IFDS facts remain distinct across the continuation.

Green dependence reaches a success parameter, a same-Promise alias, or a payload-dependent continuation return; red dependence is rejected at handler position, Promise ownership, rejection operators, or a payload-independent return. These cases distinguish continuation semantics from matching a member named \texttt{then}.

\subsection{Callback-augmented Call-chain Recovery}

For a recognized usage, call-chain recovery searches backward over ArkAnalyzer call edges, IR-level invocations missing from the graph, witnessed callback edges, and links from generated initialization methods to their owning class or component. The search stops at a framework entry, an initializer, or the first method for which no justified predecessor exists. Each chain is labeled accordingly as framework, initialization, local, or \textit{unk}. A local chain confirms the containing method but is not reported as a recovered framework-entry path.

\subsection{Sink and Taint Attachment}

For each detector occurrence $u\in U_D$, local tracing extracts statements $K_D(u)$ that may expose privacy-related data through logging, UI display, storage, network transfer, or data return. Sink resolution requires an exact configured method token and compatible receiver/namespace evidence; in particular, substring agreement such as \texttt{set} versus \texttt{setData} is rejected.

The IFDS query is configured independently by $R_T$ and its sink set. A result $q=\langle s,k,\rho\rangle$ states that the carrier bound at source $s$ may reach sink $k$ along path $\rho$. Every fact retains the source kind, API owner, carrier, SDK signature, rule origin, and normalized source location. Normal, call, continuation, return, and exceptional transfer copy this source witness unchanged, so facts from different source bindings remain distinct even when they reach the same statement.

The report distinguishes paths produced by IFDS, bounded asynchronous recovery, or both. It separately records whether Promise-success and Promise-return transfer contributed to an IFDS path. Privacy-data and framework-input paths also remain separate. A path is linked to a detector occurrence only when project, normalized location, and API identity agree; framework-input paths are never attached to privacy-API occurrences. Unlinked paths remain visible as project-level query evidence instead of being forced onto an unrelated detector record.

\paragraph{Construction invariants.}
Three invariants connect the design to the implementation. \emph{Well-formed seeding} requires every path to originate from one valid carrier and source kind. \emph{Witness preservation} keeps the original source evidence unchanged across all transfer functions. \emph{Link safety} attaches only privacy-data paths whose project, source location, and API identity agree with the detector occurrence. The loader, fact keys, transfer functions, and evidence linker enforce these properties; the evaluation checks their observable consequences through rule-resolution audits, endpoint integrity, and manual path review.

\subsubsection{Provenance Annotation}

The report stores provenance where it is produced. A call-chain edge records its call type; a query path records its producer and continuation derivations; an endpoint link records exact-statement or normalized-location agreement. Evidence assembly retains these fields instead of replacing them with a global confidence score. An asynchronous supplement therefore cannot be presented as an IFDS path, and Promise-return transfer remains distinguishable from initial Promise binding.

\subsection{Analysis Contract}
\label{subsec:analysis_contract}

\mytool's recognition claim is parameterized by ArkAnalyzer IR, the fixed API rule set, and the identity witness required by $\mathit{Accept}$. The analysis targets statically represented \arkts code; native code, dynamic loading, runtime dispatch unavailable to the frontend, and APIs absent from the rule set are outside the query domain. A recognized API establishes an executable use under this contract, while policy-level violation assessment remains a downstream audit decision.

Configured-query results are may-flows under their source/sink and reachability models. The evidence model preserves the producing transfer and admits a detector occurrence as an IFDS source only through a source-endpoint link. The solver distinguishes complete, resource-bounded, and failed analyses; only complete analyses contribute negative evidence. Edge deduplication is scoped by IR statement, value identity, access path, and source witness because same-named locals in different methods and facts from different seeds remain distinct. HapBench positive and negative cases exercise these invariants, and project isolation enforces them at corpus scale.

\subsection{Scalable Execution}

SDK declarations are loaded lazily into the Scene when taint analysis starts, keeping frontend construction independent of query-specific augmentation. Source and sink rules resolve against the designated SDK, and IFDS resource bounds remain explicit. Project isolation prevents cross-project frontend state, while phase-aware evidence retention excludes incomplete analyses from negative results.

Let $C$ be the number of executable call/property candidates, $d$ the maximum number of package/namespace-compatible rules returned by the rule index, and $k_{recv}$ the receiver-definition bound. Identity resolution costs $O(Cdk_{recv})$ time and $O(C)$ output space; in practice $d$ is small because package and namespace indexing precede member matching. The evidence carried by a source fact is immutable and constant-sized. T4 is evaluated only on resolved callback call edges and adds at most one fact per incoming source fact; its additional work is constant apart from the already available alias query. The optional unresolved-IR fallback is independently capped by source candidates, visited methods and values, emitted outcomes, and path length, and every retained fallback outcome remains labeled as supplementary.

The complete pipeline follows a fixed order: Scene construction, lifecycle modeling, report call-graph construction, import/alias extraction, API identity resolution via $\mathit{Accept}$, callback-augmented chain recovery, detector-local sink tracing, continuation-aware IFDS analysis from the lifecycle-aware \texttt{DummyMain}, optional unresolved-IR recovery, endpoint linkage, and evidence-graph assembly. A key property is that \mytool never treats a missing layer as proof of absence: if a call-chain predecessor is absent, the usage still becomes a local evidence chain; if a taint path has no compatible detector endpoint, both records remain visible but unlinked.
