\section{Evaluation}
\label{sec:evaluation}

We answer four questions:
\textbf{RQ1}~How accurately does \mytool resolve privacy-API identities, and which evidence forms account for that accuracy?
\textbf{RQ2}~How accurately do \mytool and HapFlow classify source-to-sink flows?
\textbf{RQ3}~How do IR recovery, receiver refinement, lifecycle bounds, and asynchronous recovery affect analysis quality?
\textbf{RQ4}~What evidence and scalability patterns appear across a large ArkTS corpus?
Each oracle supports a distinct claim: source-first benchmarks evaluate identity, HapBench evaluates executable flow classification, ArkAsyncBench attributes asynchronous coverage, ArkPromiseBench stresses Promise semantic boundaries, a stratified source audit evaluates real-project path semantics, and the corpus measures prevalence and cost.

\subsection{Evaluation Protocol}
\label{subsec:eval_design}

\textbf{Comparison setup.}
We compare \mytool and HapFlow using ArkAnalyzer IR and an identical source--sink query over HapBench. HapBench is evaluated with its bundled API-17 SDK, while the real-project benchmarks and corpus use OpenHarmony API-20. Each experiment uses its designated SDK without fallback, and IFDS analyzes each project as a whole.

\textbf{Identity benchmarks.}
\emph{ArkSourceFirst60} fixes ten projects from each of six project-scale/configured-import strata before detector execution. A project-wide AST pass enumerates statically named candidates compatible with the fixed rule/import universe but does not label them. Oracle construction then uses two evidence passes: source-only classification establishes executable access, package ownership, and receiver origin before detector reports are consulted; source/IR adjudication resolves ambiguous aliases and lowered receiver forms. Every accepted or rejected candidate retains its exact location, evidence excerpt, and decision reason. The resulting 186-item oracle contains 90 sensitive occurrences in 16 projects, 96 same-name or owner-incompatible negatives, and 44 confirmed-zero projects. \emph{ArkIdentityBench} contains 32 positive and 32 matched-negative cases spanning imports, typed and constructed receivers, factories, properties, compound namespaces, and package migration.

The \emph{Top-120 stress audit} complements the source-first oracle by concentrating projects with high API volume. Its 1,533 reviewed location rows canonicalize to 666 project--API keys with executable source evidence. \mytool preserves all 666 confirmed keys, so this experiment measures confirmed-key coverage under a high-volume workload.

\textbf{Flow benchmarks.}
\emph{HapBench} comprises all 67 executable cases released with HapFlow: 53 positive and 14 negative. We preserve its published case oracle and additionally audit every canonical source--sink endpoint pair reported by \mytool. \emph{ArkAsyncBench} contains 48 source-first cases: 24 positives and 24 matched negatives over callback (T1), Promise-\texttt{then} (T4), and \texttt{await} (T5) carriers. Positives pass the configured carrier, a carrier property, or an alias to a sink; negatives pass an error, constant, rejection value, ignored result, or independent same-named local. \emph{ArkPromiseBench} applies ten source-to-source boundary operators to 24 cases (seven positive and 17 negative): owner substitution, handler-position exchange, Promise alias mutation, payload-to-constant return replacement, rejection-operator insertion, chain extension and flattening, and callback registration without a trigger. Each mutant changes one semantic obligation while preserving the surrounding source and sink context.

\textbf{Real-project path audit.}
A deterministic diversity sampler constructs a 120-path audit set from 47 projects: 90 privacy-data and 30 framework-input paths; 64 IFDS, 28 supplementary, and 28 dual-provenance paths; and 23 short, 70 medium, and 27 long paths. The sample includes every network and UI path stratum. Structured source and IR review judges source identity, sink identity, explicit value dependence, reachability, and provenance; a path is correct only when all five dimensions hold. Each decision record retains both endpoints, the complete statement path, the relevant source/IR excerpts, and a reason code. Final-result rebinding preserves 118 exact paths; two deterministic replacements are reviewed from source without inherited labels, and two exact paths with strengthened provenance are rechecked against their Promise declarations.

\textbf{Large corpus.}
The corpus contains \CorpusProjects{} ArkTS projects analyzed under a common implementation, API-20 SDK, rule set, and resource policy. Its applications, libraries, and capability demonstrations expose diverse project roles and API usage patterns. Each project contributes one validated result; aggregation excludes incomplete analyses, unresolved endpoints, and invalid provenance.

\textbf{Metrics.}
Identity occurrences match on project, normalized file, line/column, canonical package/namespace/member, and access kind. Flow benchmarks report precision, recall, specificity, balanced accuracy, F1, and MCC. Exact two-sided McNemar tests compare paired predictions; Wilson intervals describe HapBench rates and corpus proportions where sampling uncertainty is meaningful. Deterministic source-first, stress, mutation, and path audits report their exact reviewed ratios rather than population confidence intervals. Corpus statistics quantify project prevalence, concentration (Gini and HHI), Spearman associations, source scope, clone sensitivity, and runtime; the preceding oracles provide the accuracy evidence.

\subsection{RQ1: Privacy-API Identity}
\label{subsec:api_detection_accuracy}

\textbf{Source-first accuracy.}
Within the fixed rule set and statically enumerable candidate universe, \mytool reports exactly the 90 gold occurrences in ArkSourceFirst60: TP/FP/FN$=90/0/0$, for 100\% observed precision, recall, and F1. It also classifies all 16 positive and 44 zero projects correctly. Exact-location matching prevents one call from masking a missed occurrence elsewhere in the same file.

The gold set contains 44 executable namespace properties, 26 namespace calls, 11 typed receivers, four constructed receivers, three manager receivers, and two factory receivers. Thus, 20/90 occurrences require receiver evidence beyond the accepted line's namespace syntax, and nearly half are property reads rather than calls. The 96 negatives stress the complementary boundary: application wrappers, UI controllers, collections, test drivers, and third-party methods reuse generic members such as \texttt{create}, \texttt{on}, \texttt{request}, and \texttt{getData}.

\textbf{High-volume reproduction.}
\mytool recovers all 666 manually confirmed project--API keys in the Top-120 stress audit (100\% confirmed-key coverage), including 558 namespace-qualified, 102 member/receiver, five template-expression, and one compound-qualified key. The controlled benchmark attributes this result to the composition of package, receiver, factory, property, and IR evidence; the stress audit adds 102 confirmed member/receiver keys and shows that the evaluated detector configuration preserves all 666 previously confirmed high-volume keys.

\textbf{Where the classifications differ.}
ArkTS-specific IR recovery resolves the anonymous initializer and exceptional successor missed by HapFlow, while constant-index access paths, receiver-refined dispatch, and bounded lifecycle transitions remove its array, virtual-target, and cross-event false positives.
