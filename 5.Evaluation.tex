\section{Evaluation}
\label{sec:evaluation}

We evaluate four questions:
\textbf{RQ1}~How accurately does \mytool resolve privacy-API identities in real projects, and which evidence forms produce that accuracy?
\textbf{RQ2}~How accurately do \mytool and the author-released HapFlow artifact classify end-to-end flows?
\textbf{RQ3}~Which recovery mechanisms account for \mytool's behavior, and what precision--recall trade-offs do they introduce?
\textbf{RQ4}~What privacy-evidence patterns and scalability characteristics appear in a large OpenHarmony corpus?
We separate these claims: source-first and controlled identity benchmarks support API recognition, HapBench and ArkAsyncBench support flow classification and mechanism attribution, and the corpus supports prevalence and scalability rather than ground-truth accuracy.

\subsection{Experimental Design}
\label{subsec:eval_design}

\textbf{Implementations and configuration.}
We evaluate the author-released HapFlow artifact and the released \mytool implementation. Both consume ArkAnalyzer IR and the same HapBench source--sink query. For artifact comparability, HapBench uses the OpenHarmony API-17 SDK (version 5.0.5.165) bundled with the HapFlow release; the corpus experiment uses the independently installed API-20 SDK (version 6.0.0.47). SDK fallback is disabled, and both directory fingerprints are retained. The large-corpus runner launches one analyzer process per project, with two concurrent workers, so that heap state and failures are isolated across projects. HapBench uses the bounded lifecycle policy and unbatched IFDS solver described in Section~\ref{sec:implementation}. The main configuration enables the supplementary callback scan; a paired callback-off run isolates its contribution from the IR/IFDS analysis.

The final corpus artifact is produced by one process-isolated execution of the final build over the 1,014 retained projects; no change-impact overlay enters the reported aggregates. The run manifest records the analyzer revision and build hash, rule hashes, SDK fingerprint, feature flags, resource limits, and excluded partial project. Every retained log identifies the API-20 SDK, completes PTA, and reports a single unbatched IFDS run without budget exhaustion.

\textbf{Evaluation units.}
We use six complementary evidence sets. \emph{ArkSourceFirst60} is an output-independent real-project benchmark. Before running the evaluated detector, we deterministically sample 60 projects across small, medium, and large source-tree strata: 30 contain an import compatible with the frozen API rules and 30 do not. A structured AST queue locates executable member accesses but assigns no label. Manual source review then accepts or rejects all 101 candidates using imports, receiver definitions, factory origins, SDK types, and access context, and inspects configured imports in candidate-free projects. The resulting occurrence-level gold set contains 90 accepted accesses in 16 projects, 11 high-confusion rejected candidates, and 44 projects with no configured sensitive access. Every gold record stores project, file hash, exact line and column, canonical API identity, access kind, receiver/source expression, category, permission, and the imports used during review.

\emph{ArkIdentityBench} contains 32 positive and 32 matched-negative cases spanning namespace calls, properties, typed and constructed receivers, factory-returned managers, compound namespaces, aliases, and historical-to-consolidated package migration. Its progression baselines successively add lexical, import, declared-receiver, and factory evidence under the same case oracle. It isolates identity-resolution mechanisms from downstream call-graph and taint behavior.

The \emph{120-project high-output audit} complements source-first coverage with a stress population rich in reported identities. It contains 666 manually confirmed project--API keys backed by executable source locations. Because the ranking begins from \mytool output and canonicalizes repeated occurrences to project--API keys, this secondary artifact supports stress precision rather than occurrence recall.

\emph{HapBench} is the complete 67-case suite distributed with HapFlow: 53 expected-flow and 14 expected-no-flow cases in seven categories. We reconstruct the oracle from each case's inline source, sink, and leak/no-leak annotations and cross-check the category totals against the paper. We publish the case-level oracle and preserve disagreements with the executable artifact.

\emph{ArkAsyncBench} is a source-first controlled benchmark fixed before executing the evaluated configurations. Its 48 cases use three configured privacy-data APIs---advertising identifier, SIM account information, and reverse geocoding---under callback (T1), Promise \texttt{then} (T4), and \texttt{await} (T5) constructs. The 24 positive cases pass the configured carrier, a carrier property, or a carrier alias to \texttt{console.info}; the 24 matched negatives pass only an error, constant, rejection value, ignored result, or similarly named independent local. The oracle is therefore defined by explicit source-level value dependence rather than by either configuration's output. This benchmark isolates the implemented asynchronous rules; it does not claim completeness over all event-loop or Promise semantics.

The \emph{large corpus} begins with 1,015 OpenHarmony/ArkTS project directories. Of these, 1,014 satisfy the complete-analysis criterion and cover 31,205 files and 233,894 methods. One project reaches the unbatched IFDS time bound after successful PTA and is retained as a partial artifact but excluded from aggregate analysis. A token-based redundancy analysis removes comments and trivia but preserves identifiers and literals, then computes SHA-256 file fingerprints, exact project-clone clusters, and near-clone clusters. This evidence supports prevalence, concentration, robustness, and cost analyses rather than ground-truth accuracy.

\textbf{Metrics and statistics.}
At the identity-occurrence level, equality requires project, normalized file, exact line, canonical package/namespace/member, and access kind; a nearby call to the same API cannot mask a missed occurrence. Project-level identity results count both API-positive and confirmed-zero projects. At the HapBench and ArkAsyncBench case levels, a positive prediction means that at least one privacy-data source-to-sink path is reported; framework-input paths cannot satisfy either oracle. We report precision, recall, specificity, balanced accuracy, F1, and MCC, with Wilson intervals for binomial metrics and exact two-sided McNemar tests for paired outcomes. For the high-output audit, we retain project-key and project-level Wilson intervals but do not reinterpret its canonicalized keys as occurrence recall.

\subsection{RQ1: Privacy-API Identity Resolution}
\label{subsec:api_accuracy}

\textbf{Source-first real-project accuracy.}
\mytool reports exactly the 90 gold occurrences in ArkSourceFirst60: TP/FP/FN$=90/0/0$, yielding 100\% observed occurrence precision, recall, and F1 (95\% Wilson CI for precision and recall: 95.91--100\%). At project level it classifies all 16 positive and 44 zero projects correctly. Exact-location matching matters here: IR statement locations are post-resolved to the corresponding executable AST access, preventing one detected access from covering another same-API access elsewhere in the file.

The gold set spans 44 namespace properties, 26 namespace calls, 11 typed receivers, four constructed receivers, three manager receivers, and two factory receivers. Thus, 20/90 occurrences require receiver evidence unavailable from the accepted line's bare namespace syntax, while nearly half are executable properties rather than calls. The 11 rejected candidates exercise the complementary precision boundary: same-name application wrappers, collection/controller operations, and library calls such as \texttt{create}, \texttt{on}, \texttt{off}, and \texttt{getData} are excluded when their package and receiver origins do not establish a configured identity.

\textbf{Mechanism progression.}
Table~\ref{tab:identity_progression} quantifies how evidence changes the decision boundary on ArkIdentityBench. A lexical matcher finds every positive but also every matched collision. Import evidence removes those collisions yet reaches only 17/32 positives; declared receiver types recover nine more, and factory tracing recovers another two. The complete resolver adds constructed receivers, executable properties, compound aliases, and namespace-constrained migration, classifying all 64 cases correctly.

\textbf{High-output stress audit.}
All 666 reviewed project--API keys in the 120-project stress population have an executable supporting access (100\% observed project-key precision; 95\% Wilson lower bound 99.43\%). All 120 projects contain only confirmed keys (project-level lower bound 96.90\%). Its evidence tags include 558 namespace-qualified accesses, 102 member/receiver accesses, five executable template accesses, and one compound-qualified call. This distinct aggregation unit strengthens precision evidence under dense output without replacing the occurrence-level source-first benchmark.

Figure~\ref{fig:running_design} illustrates the evidence composition on a compact example: \texttt{deviceInfo.brand} is an executable property, whereas \texttt{helper.createAsset()} requires a definition chain to \texttt{photoAccessHelper.getPhotoAccessHelper(...)}. At the schema level, the released HapFlow loader has no field/property source form or detector-style factory witness; the executable, same-SDK end-to-end comparison is reported separately in RQ2.

\noindent\textbf{Answer to RQ1.}
On the source-first sample, \mytool resolves all 90 manually accepted occurrences at exact locations and rejects all candidate collisions, including 44 zero projects. Controlled progression shows that its gain comes from composing package, receiver, factory, property, and IR identity evidence rather than relaxing member-name matching. The 120-project stress audit supplies consistent high-volume precision evidence over 666 additional project--API keys.

\textbf{Error mechanisms.}
HapFlow's two false negatives expose omitted anonymous-instance initialization and exceptional-flow recovery. Its four false positives arise from collapsing distinct array indices, imprecise virtual dispatch in two cases, and a lifecycle edge that makes \texttt{UnreachableFlow} reachable. \mytool repairs these mechanisms through constructor-to-instance-initializer edges, lexical-environment and exception propagation, constant-index access paths, receiver-refined dispatch, and bounded lifecycle transitions.

\mytool's three false negatives are all lifecycle cases. Source inspection reveals that they also stress the oracle semantics. In \texttt{ActivityLifecycle4}, a child override does not invoke the parent source-bearing \texttt{onCreate}; \texttt{BackupExtensionAbility} requires an instance field to survive into a later restore instance; and \texttt{Button1} requires static state written by a click callback to reach a later ability creation. We retain the published/source-annotated positive labels, report all three as false negatives, and do not add unconstrained edges solely to match them.

Because these labels depend on object and event-order assumptions, Appendix~\ref{subsec:app_oracle_sensitivity} repeats the comparison under a strict executed-order contract that relabels only these three cases. Under this secondary, post-hoc sensitivity oracle, \mytool classifies all 67 cases correctly, whereas HapFlow classifies 58 (48 TP, 10 TN, 7 FP, and 2 FN); the exact paired test gives $p=0.00390625$. We retain the published labels as the primary result and use this sensitivity analysis only to expose how lifecycle semantics affect the comparison.

\noindent\textbf{Answer to RQ2.}
On the complete executable suite, \mytool attains 100\% precision, 94.34\% recall, and 97.09\% F1 with no false positives. Its principal empirical advantage over the released HapFlow artifact is negative-case discrimination, reflected in higher specificity, balanced accuracy, and MCC.

\label{subsec:component_ablation}

\textbf{HapBench isolates core recovery mechanisms.}
The complete suite attributes its configuration differences to IR, dispatch, and lifecycle recovery. Its callback constructs already have explicit core-IFDS edges, so disabling the supplement preserves the same 50 positive cases and 53 unique paths. We therefore evaluate incremental asynchronous coverage with a benchmark constructed around continuation gaps rather than assigning that role to HapBench.

\textbf{ArkAsyncBench exposes complementary coverage.}
Table~\ref{tab:asyncbench} separates paths supported by core IFDS from those reconstructed by the asynchronous supplement. The full configuration classifies all 24 positive and 24 matched-negative cases correctly. T1 callbacks and T5 \texttt{await} bridges are independently supported by both analyses, while all nine T4 \texttt{then} positives are supplement-exclusive. Removing the supplement therefore preserves 15 core-supported positives but misses the nine T4 cases (exact McNemar $p=0.00390625$). This decomposition turns provenance into a mechanism check: \textsc{Both} marks corroborated T1/T5 paths, and \textsc{AsyncSupplement} identifies the unique T4 increment.

\textbf{Real-project asynchronous diagnostic.}
We rerun 26 callback-heavy real projects with the final typed-source configuration. It produces nine privacy-data paths in five projects, including eight asynchronous-only paths; twelve framework-input paths remain a separate source universe. Manual source/IR review confirms all eight structured dependencies (95\% Wilson lower bound 67.56\%): one T1 callback carries \texttt{metadata.genre}, one T4 Promise carries an advertising identifier through a field assignment, and six T5 paths carry awaited media metadata or reverse-geocoding results into log arguments. These real-code instances align each controlled construct with an executable application pattern.

\textbf{IR recovery is necessary.}
Removing constructor/initializer, lexical-capture, exception, array, and alias recovery creates 13 additional false negatives. F1 falls by 14.87 points and MCC by 0.310. The full configuration is exclusively correct on 13 cases and never exclusively wrong relative to this ablation (exact McNemar $p=0.000244$). This remains significant under Bonferroni correction for the four pre-specified ablations ($\alpha=0.0125$). The affected cases span anonymous constructs, closures, exception handling, array copying, multi-field access, and virtual dispatch, showing that the gain is not concentrated in a single hand-written pattern.

\textbf{Receiver refinement protects specificity.}
Without receiver-sensitive target filtering, \texttt{VirtualDispatch3} becomes a false positive. Recall is unchanged, but specificity falls from 100\% to 92.86\% and MCC from 0.881 to 0.831. This single controlled counterexample is important for privacy analysis: resolving more targets is not automatically an improvement when unrelated implementations introduce spurious source-to-sink paths.

\textbf{Lifecycle bounds encode a precision policy.}
The unrestricted lifecycle variant accepts two additional cross-event cases, but also reintroduces the explicit \texttt{UnreachableFlow} false positive. Because F1 ignores true negatives in a 53-positive/14-negative suite, its raw F1 rises to 98.11\% even as specificity falls to 92.86\% and balanced accuracy to 95.49\%; the bounded configuration retains 100\% specificity and 97.17\% balanced accuracy. Under the strict executed-order sensitivity oracle in Appendix~\ref{subsec:app_oracle_sensitivity}, bounded \mytool classifies 67/67 cases, whereas unbounded lifecycle creates three cross-event false positives and classifies 64/67. The bounded default therefore enforces the paper's precision-first reachability contract.

\noindent\textbf{Answer to RQ3.}
IR recovery provides the largest statistically supported HapBench contribution, receiver refinement removes a concrete dispatch false positive, and bounded lifecycle preserves perfect negative-case discrimination. On ArkAsyncBench, the asynchronous supplement independently supports every positive carrier, uniquely recovers all nine T4 Promise-\texttt{then} cases, and introduces no negative-case errors; eight corresponding paths are confirmed in real projects.

\subsection{RQ4: Large-Corpus Characterization}
\label{subsec:corpus_patterns}

The retained analysis covers 31,205 ArkTS/TypeScript files and 233,894 methods in 1,014 projects. It identifies 1,896 detector-recognized privacy-API occurrences in 273 projects, 1,542 detector-local sink observations in 185 projects, and 1,103 configured-query source-to-sink may-paths in 257 projects. The path total combines core solver outcomes and separately provenance-labeled asynchronous supplements. Detector-local sinks are attached to detector usages; configured-query paths use \texttt{hapflow\_sources.json}/\texttt{hapflow\_sinks.json}. They are therefore separate evidence universes, and the 257 versus 185 project counts do not assert that a path exists without a configured sink endpoint. The final-run audit verifies valid path endpoints, provenance tags, and detector-to-path link indices. These records are \emph{audit evidence}, not confirmed leaks.

\textbf{Concentration and category structure.}
The distribution is long-tailed: the median project has no recognized privacy API, while the top 10 projects account for 26.42\% of occurrences and the top 50 account for 59.44\%. The API-occurrence Gini coefficient is 0.886; the corresponding HHI is 0.0121, equivalent to 82.9 equally sized contributing projects. Hardware identity, network connectivity, screen/display identity, account data, and clipboard data contribute 18.62\%, 14.40\%, 11.71\%, 9.49\%, and 5.96\%, respectively. Project scale is associated with evidence volume (Spearman $\rho=0.461$ between method count and API occurrences), but the dispersion in Figure~\ref{fig:eval_corpus_landscape} shows that size alone is not a reliable privacy proxy.

\textbf{Destinations and path structure.}
Logging dominates the 1,542 detector-local sink observations (1,272; 82.49\%), followed by UI display (136; 8.82\%), storage (93; 6.03\%), data return (32; 2.08\%), and network transmission (9; 0.58\%). This distribution characterizes detector-local audit destinations and is not used to label the endpoints of all 1,103 configured-query paths. Call chains have median length 1 and P95 length 4; configured-query paths have median length 5, P95 length 9, and maximum length 33.

\textbf{Solver integrity and cost.}
All 1,014 retained projects finish with \texttt{SUCCESS}; no retained log contains a PTA fallback, IFDS batching, or budget exhaustion. The median project processes 837 IFDS edges (P95 13,857; maximum 778,986). Exact flow deduplication reduces 1,549 raw paths to 1,103 unique paths. Median per-project wall time is 16.4\,s, P95 is 21.2\,s, and the 351.3\,s maximum belongs to the 10,757-method outlier. The moderate method-count/runtime association (Spearman $\rho=0.393$) reflects both project scale and fixed frontend/SDK costs.

\textbf{Clone sensitivity.}
The token profile over the 1,015 candidate directories contains 32,233 source files, 21,663 unique token fingerprints, nine exact-clone clusters, and eleven near-clone clusters. Over the 1,014 completed analyses, counting one representative per exact-clone cluster changes API-, sink-, and path-positive project rates from 26.923\%, 18.245\%, and 25.345\% to 27.236\%, 18.392\%, and 25.628\%, respectively. Using one representative per near-clone cluster yields 27.090\%, 18.328\%, and 25.680\%. The maximum absolute shift is 0.335 percentage points. The aggregate prevalence therefore does not arise from repeatedly counting a small number of copied demonstrations, although shared framework code can still influence individual category frequencies.

\noindent\textbf{Answer to RQ4.}
Privacy evidence is sparse across projects but concentrated within a small high-output tail. Local logging is the dominant destination, project size only partially explains evidence volume, and clone-aware resampling leaves project-level rates essentially unchanged.
