\subsection{Failure Modes Observed in a Large-scale Corpus}
\label{subsec:app_failure_modes}

Before designing \mytool, we repeatedly ran the ArkAnalyzer/HapFlow-based pipeline on the large-scale dataset and inspected failures. The most common failure modes were:

\begin{itemize}
    \item \textbf{Layout misses.} Some projects contained valid \arkts source files but were not discovered by standard project construction.
    \item \textbf{Package migration misses.} Rules written for \texttt{@kit.*} packages missed apps importing equivalent historical \texttt{@ohos.*} packages, and vice versa.
    \item \textbf{IR-lowering misses.} Multi-segment API expressions were lowered into temporaries, causing the final method call to lose its namespace context.
    \item \textbf{Indirect receiver misses.} Manager APIs were called through objects whose types were absent, imprecise, or not directly tied to the original namespace.
    \item \textbf{Callback-edge misses.} Anonymous functions and field-stored callbacks were not always connected to their registration sites in the recovered call chain.
    \item \textbf{Callback taint loss.} Runs without callback/Promise taint propagation undercounted or eliminated taint flows even when source and sink rules loaded correctly.
\end{itemize}

These failure modes motivate the design in Section~\ref{sec:design} and provide natural ablation points: each optimization can be disabled to measure its effect on API recall, chain coverage, sink attachment, or taint-flow count.

\subsection{Context-Sensitive Call Graph Details}
\label{subsec:app_context_sensitive}

Context-insensitive call graphs (CHA, RTA) merge all calling contexts of a method into a single node, causing spurious data flow at merge points. \mytool supports $k$-limited context-sensitive call graph construction using ArkAnalyzer's pointer analysis infrastructure. The context sensitivity level $k$ controls the depth of calling context tracked for each method invocation. At $k=0$, the analysis is context-insensitive (equivalent to CHA). At $k=1$, each call site receives its own context, which is sufficient to separate most callback-related data flows. At $k=2$, calling contexts are tracked two levels deep, which helps with nested callback patterns.

\subsection{Micro-benchmark Detailed Results}
\label{subsec:app_micro_details}

Three failure modes are isolated in the ArkPrismBench-Micro: (1)~M08 (Promise .then()) misses 2 positive cases where the callback is defined in a separate method from the \texttt{.then()} call---our current Promise chain analysis only handles inline and variable-chained callbacks; (2)~M06 (same-name negative) produces 2 false positives where user-defined methods sharing names with privacy APIs (\texttt{getCurrentLocation()}) are incorrectly matched---this motivates receiver-type-aware filtering; (3)~M07 (string/comment) correctly rejects all cases, confirming that the recognizer does not match non-executable references.

Aggregating the asynchronous-pattern categories (M08--M13), callback target resolution achieves 18/20 correct targets (90.0\% resolution accuracy), and tainted-parameter binding achieves 17/20 (85.0\%). Promise edge precision is 100.0\% (2/2), while Promise edge recall is 50.0\% (2/4), reflecting the cross-method gap.

Table~\ref{tab:detector_contribution} (Section~\ref{subsec:api_accuracy}) decomposes detections by detector category, reports a cumulative coverage view on the full corpus, and provides a leave-one-out ablation on the ArkPrismBench manual benchmark. The leave-one-out ablation confirms that each family is irreplaceable: removing any single family drops method recall below 86\% and usage recall below 84\%.

\subsection{Manual Audit Details}
\label{subsec:app_manual_audit}

The ArkPrismBench benchmark uses stratified random sampling rather than purposive selection, ensuring that zero-output and low-output projects are represented. However, the sampling strata are defined by \mytool's raw API count, and \mytool's reports serve as navigation aids during annotation; the benchmark is therefore \emph{not fully independent} of the tool. The annotation itself is source-first: annotators label based on code inspection, not tool output, but the tool's reports influence which code regions receive the most attention.

\paragraph{Recall scope.} Recall is measured against the manually accepted project-level namespace+method gold set for all 164 sampled projects. For the zero-output stratum (40 projects), annotators confirmed that no privacy-sensitive API usage exists in the source code, verifying that \mytool did not miss any APIs in these projects. For the positive strata, annotators identified all privacy API usages in the source, including those \mytool may have missed.

\paragraph{Zero-output statistical bound.} The 40 zero-output projects represent a sample from 802 zero-output projects in the corpus. While no false negatives were found in the sample, the rule-of-three method~\cite{hanley1983if} gives a 95\% confidence upper bound of $3/40 = 7.5\%$ on the false-negative rate among unsampled zero-output projects. We therefore cannot claim that all 802 zero-output projects are FN-free; we can only claim zero FN within the sampled 40.

\paragraph{Negative benchmark coverage.} The zero-output stratum covers 40 projects where \mytool detected nothing. Manual inspection confirmed that none contained a privacy API usage matching any of the 21 categories. This check covers direct-call, property-read, and indirect-invoke patterns (the latter through manual code inspection rather than grep, since indirect-invoke patterns require semantic resolution).

\paragraph{Annotation quality.} Two annotators independently labeled each project. Inter-annotator agreement on the positive strata was $\kappa = 0.91$ (Cohen's kappa), with disagreements resolved by joint re-inspection. Common disagreement sources were: helper receiver calls where the API is accessed through a factory-returned object, and property constants whose names resemble ordinary UI fields.

The runtime distribution is right-skewed: 75\% of projects complete within 32.7\,s, and 95\% within 39\,s. The longest project (\texttt{aloeplayer\_ohos}, 270.8\,s) is an outlier with 10 privacy APIs and a large method count that triggers extensive IFDS propagation. The two solver failures are caused by unresolvable ArkTS IR structures in those projects; they do not affect other projects because of process isolation.

The dominant cost is IFDS taint analysis, which accounts for the majority of per-project time. Scene construction (ArkAnalyzer IR loading) is the second-largest cost, typically consuming 40--60\% of the total. Call-graph construction (CHA) is negligible at a median of 3\,ms per project. Callback analysis adds minimal overhead because it operates on the already-constructed IR. PTA at $k=1$ adds 5.02$\times$ overhead relative to CHA alone, but CHA itself is a small fraction of total runtime; the effective overhead of PTA over the full pipeline is therefore modest. The fact that $k=2$ is faster than $k=1$ (34,473\,ms vs.\ 46,870\,ms) is counter-intuitive; a likely explanation is that the deeper context reduces the number of spurious call targets per site, lowering the total work despite the larger context depth.

The estimated two-worker wall time for 1,015 projects is 15,071\,s ($\approx$4.2\,h), suggesting near-linear scaling with worker count. The process-per-project isolation strategy prevents memory accumulation across projects, but imposes a per-project startup cost. For a hypothetical 10,000-project marketplace corpus, the projected wall time with 4 workers is $\approx$8.4\,h, well within overnight-batch feasibility.
