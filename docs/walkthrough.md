# ArkPrism 实现走读

这份文档不讲代码细节，而是按“分析器实际怎么工作”的顺序解释 ArkPrism。

## 1. 它在解决什么问题

ArkPrism 不是一个简单的 API 检索器。它要解决的是另一类问题：

- 一个 HarmonyOS 应用到底在什么地方接触了隐私能力。
- 这些能力是页面初始化时自动触发，还是用户交互后触发。
- 拿到的数据有没有继续发到网络、写日志、写本地或展示到界面。
- 多类隐私数据是不是在同一段业务逻辑里组合出现。

换句话说，它不是只找“点”，而是在恢复“行为链”。

## 2. 它先把项目转成适合分析的结构

ArkPrism 的第一步不是扫字符串，而是通过 ArkAnalyzer 把项目转成统一的程序表示。这样后面的分析才能回答这些问题：

- 这条语句属于哪个方法。
- 这个调用的接收者类型是什么。
- 两个方法之间有没有真实调用关系。
- 这段逻辑是在 `if`、循环还是异常块里。

如果没有这层结构化表示，后面的结果只能停留在模糊匹配。

## 3. 它先找隐私触点，再继续追踪上下文

对每个源码文件，ArkPrism 先看文件真正导入了哪些系统包，再只针对这些包对应的规则做检测。这样做的目的是把候选范围压小，减少误报。

当前它会识别四类情况：

1. 直接调用系统隐私 API。
2. 把隐私 API 的返回值赋给变量。
3. 通过 manager / service 对象间接调用隐私能力。
4. 读取隐私相关常量或字段。

做到这里，它已经知道“哪些地方碰了隐私能力”，但还不知道这些能力是从哪里被触发的。

## 4. 真正关键的是把断掉的调用链接起来

HarmonyOS ArkTS 项目里，很多真实逻辑都不是简单的方法互调，而是藏在这些位置：

- ArkUI 的事件回调
- 匿名函数
- `%AM...` 形式的编译后匿名方法
- Promise 的 `then/catch/finally`
- 页面或组件生命周期

如果只依赖原生调用图，很多 API 看起来会像孤立点。因为工具只能看见“这个方法里有调用”，却看不见它是如何和页面、按钮、异步回调连在一起的。

ArkPrism 的做法是自己重建一张增强反向调用图。

它先吃进原生调用图里已经存在的边，然后继续补这些最容易漏掉的关系：

- 某个调用把函数作为参数传入时，这个函数本身是后续回调。
- IR 文本里出现 `%AM...` 时，说明这里引用了匿名方法。
- Promise 的链式回调需要手工接上。
- 对已确认可达的方法继续扫描显式调用语句，把原生调用图漏掉的 API 终点补回来。

这一步是当前实现最核心的价值所在。

## 5. 为什么“只扫描可达方法”很重要

补边最简单的办法是把全工程所有 `invoke` 都扫一遍，但那样会把死代码、实验代码、废弃逻辑一起卷进来，噪声会非常大。

ArkPrism 没这么做。它先从入口方法开始，得到一个可达方法集合，然后只对这部分方法继续扩展调用边。这样既能补回 SDK 终点和匿名回调，又不会把明显不可能执行的路径大量引入。

这也是为什么它适合做真实应用分析，而不是只做课堂级示例。

## 6. 调用链不仅有路径，还有行为解释

得到入口到 API 的调用链之后，ArkPrism 还会继续补两层解释信息。

第一层是控制结构信息。它会判断 API 调用是不是出现在：

- 某个条件分支里
- 某个循环里
- 某个 `try-catch` 结构里

这样报告里就不只是“调用了 API”，而是可以进一步说：

- 调用前有权限判断
- 调用发生在异常回退逻辑里
- 调用可能在循环中多次发生

第二层是语义上下文。它会尝试跳过 `build`、默认方法、匿名包装层这些弱语义节点，定位到更像真实业务动作的方法名，比如“选择联系人”“读取蓝牙状态”“获取网络能力”等。

最后形成的不是抽象签名堆，而是更接近人类读代码时的理解路径。

## 7. 然后它继续问：数据后来去了哪

找到隐私调用之后，下一步自然是看这些数据有没有继续外流。

ArkPrism 在这一步先采用轻量策略：

1. 找出隐私 API 的结果被赋给哪个变量。
2. 再看这个变量有没有流进网络、存储、日志、界面或返回语句。
3. 如果值被挂到 `this.xxx` 字段上，再去同一个类的其它方法里继续找。

它不是完整污点分析，但对工程场景很实用。因为很多风险行为正好就发生在这些明显的发送、写入、展示或日志输出位置。

## 8. 它还会识别“协同行为”

单独读取某一个隐私类别，有时很难直接下结论。但如果联系人、设备标识、网络状态、传感器状态这些信息在同一逻辑里组合出现，含义就不一样了。

ArkPrism 的多源协同分析就是在做这件事。

它会按 `profilingCategory` 归类，然后从近到远看这些类别是不是：

- 在同一个方法里一起出现
- 在不同方法里，但汇合到同一个上游祖先方法
- 至少出现在同一个文件的同一段业务中
- 或者在整个应用范围内形成多类聚合

这样它输出的不再是“很多离散 API”，而是“一个可能在组合使用多类数据的业务结构”。

## 9. 权限分析在当前版本里只是补充背景

ArkPrism 还会读取 `module.json5` 里的权限声明和理由文本，并解析 `$string:xxx` 这种资源引用。

但要明确：当前版本不会自动判断 API 是否缺权限、权限是否冗余，也不会做权限与调用行为的一致性审计。

所以它提供的是“配置侧背景”，不是最终的权限合规裁定。

## 10. HapFlow 是更强但可选的后续阶段

前面的 sink 扫描偏轻量，适合快速建立画像。若环境允许，ArkPrism 还可以继续启动 HapFlow，做更精确的跨过程 IFDS 污点分析。

这一步会处理更复杂的传播场景，例如：

- 参数传递
- 返回值回传
- 对象字段传播
- 闭包与回调传播
- 容器传播
- 指针分析支持下的别名扩散

但它依赖 SDK 和 source/sink 规则，所以不是每次运行都会真正产出 taint flow。

## 11. 最终输出的不是单一清单，而是一份行为画像

到最后，ArkPrism 交付的是一组相互补充的信息：

- 哪些隐私 API 被命中
- 每个 API 的入口到终点调用链
- 调用时的控制流上下文
- 数据是否继续流向 sink
- 多个隐私类别是否形成协同
- 工程声明了哪些权限和理由
- 如果开启 HapFlow，是否存在更精确的 taint path

这套输出比“命中了哪些 API”更接近真实审计需要的信息密度。

## 12. 一句话总结

ArkPrism 的实现思路是：

先用结构化静态分析定位隐私触点，再通过增强调用图把这些触点还原成页面和业务上下文里的真实行为链，然后继续补上数据去向、多源协同、权限背景与可选的精确污点传播，最终输出可解释的隐私行为画像。
